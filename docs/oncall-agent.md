# T15 bounded custom on-call agent

The custom Python agent is `app.oncall_agent.OnCallAgent`, automatically scheduled
by the authenticated Alertmanager webhook. It is a deterministic agent workflow,
not an LLM inference or a manually launched diagnosis script. Existing T14 rule,
thresholds, routing, private receipt volume and deduplication remain in use.

The bounded workflow is: confirm the fingerprint/start time/allowlisted labels
against Alertmanager's private active-incident API; read redacted application
diagnostics; validate development environment, exact exercise ID, activation time,
expiry, known `analysis_disabled` cause and unused repair allowance; clear that
one flag; call the same persisted analysis workflow on a separate authorized
synthetic request; require validated pending suggestions and zero active tasks.
The agent has four fixed HTTP tools, no URL arguments, shell, file repair, code
execution, deployment or database credentials. It cannot activate an exercise or
approve tasks. Diagnostics expose only enums, scope identifiers, counts and times.
The agent does not follow alert annotations or generator URLs.

`EXERCISE_ADMIN_TOKEN_FILE` is a separate maintainer-only secret for authorizing
and disabling an exercise. `ONCALL_OPS_TOKEN_FILE` grants only diagnosis, a scoped
clear and one verification. Neither demo sessions nor the existing read-only ops
credential authorize these actions. The frontend already blocks `/api/v1/ops`;
the direct API is loopback-only. Receiver and Alertmanager have no host ports.
Secrets are generated by `python scripts/configure_observability.py`, preserved
when present, ignored by Git and never passed to the agent as alert content.

Authorization is disabled by default (`ENABLE_ONCALL_EXERCISE=false`). Enabling
the gate alone causes no fault. A maintainer must separately submit a strict
development-only scope: one exercise UUID, the only permitted flag, expiry no
later than 240 seconds, a new synthetic user's affected request and a distinct
synthetic verification request. Both requests must be owned, unanalyzed and have
no active tasks. The flag affects only that user/request's analysis POST, before
any provider call; viewing and other requests remain available. It expires after
240 seconds at most and has at most 40 failed attempts. The flag and authorization
are process-local and fail closed on API restart. Cleanup closes the gate.

A durable incident claim precedes diagnostic/action calls, so concurrent/repeated
webhooks and listener restart cannot retry a repair. The API also atomically
enforces the single clear and single verification per scope. Agent audit records
contain fixed event names, timestamps, outcome and bounded reason enums only;
they share the existing private SQLite volume and 500-record/seven-day bounds.
A crash may leave a `running` record; it deliberately does not resume a repair.
Unknown cause, invalid/stale identity, missing/expired scope, production mode,
HTTP failure or failed verification stops and records failure without other fixes.
Whole workflow deadline is 45 seconds; verification retains the analysis maximum
of 30 seconds (or the shorter remaining authorization). Automatic tests remain
simulated and real-PostgreSQL tests use the isolated test database.

## Exact live exercise proposed for human approval

This section is a plan, **not authorization or executed evidence**.

- Environment: local Docker Compose project `officeflow`, `APP_ENV=development`,
  API `127.0.0.1:8000`, frontend `127.0.0.1:8080`, existing private PostgreSQL.
  No production deployment, paid service, model download or real Ollama call.
- Impact: one newly generated synthetic account and its one newly created request
  receive analysis HTTP 503; viewing and unrelated users/requests stay available.
- Maximum fault/authorization duration: **240 seconds**, at most **40** synthetic
  failed attempts. Observation including alert resolution is bounded separately
  (190 seconds for repair, 40 for verification, 180 for resolution, 30 for receipt).
- Agent's only permitted repair: clear `analysis_disabled` **once**, for that exact
  scope after real Alertmanager delivery and known-cause diagnosis. It then makes
  one synthetic analysis check, persisting inactive suggestions only. The verifier
  also demonstrates one normal user analysis after the agent clears the flag.
- Cleanup: disable the entire exercise gate and recreate only the API, preserving
  volumes, credentials, saved requests and tasks. Cleanup is not counted as repair.
  Any failed automatic step is reported as failure; no substitute repair is tried.

After explicit human approval, the maintainer can run:
`python scripts/verify_oncall.py --approval-reference "<reference to explicit approval>"`.
The reference is an audit aid, not a substitute for human approval. Do not execute
this command during implementation or automatic CI. Evidence is written to ignored
`artifacts/t15-verification.json`: actual failure/alert/invocation/diagnosis/clear/
verification/user-recovery/resolution timestamps, deduplication and redaction checks.
Never claim the live demonstration succeeded from isolated tests alone.

Tests: `docker compose --profile test run --build --rm test`.
Required CI jobs remain Backend checks and Frontend checks.
